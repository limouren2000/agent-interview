1. synchronized 和 ReentrantLock 有什么区别？
• 共同点：都能实现线程互斥，保证临界区操作的可见性，并且都支持可重入。
• 底层机制：synchronized 是 JVM 内置锁，涉及对象监视器 Monitor；ReentrantLock 是 JUC 显式锁，主要基于 AQS 实现。
• 功能区别：ReentrantLock 支持可中断获取锁、超时尝试、公平锁和多个 Condition；synchronized 自动获取和释放锁，使用更简洁。
• 选择建议：普通同步优先使用 synchronized；需要精细控制锁获取或条件等待时选择 ReentrantLock，注意在 finally 中解锁。

2. 线程池打满但 CPU 很低，怎么排查？
• 先看指标：确认 activeCount、maximumPoolSize、queueSize、拒绝次数和任务完成速率，判断是否持续饱和。
• 抓线程栈：连续采集 jstack 或 jcmd，判断线程集中在锁等待、Future 等待、数据库连接等待，还是 Socket I/O。
• 查外部依赖：结合 RPC、MySQL、Redis 的耗时和连接池指标，定位慢调用、资源竞争或线程池嵌套等待。
• 注意误区：线程池满不等于 CPU 忙；若线程池规模远小于 CPU 核数，也可能出现线程都在计算但整体 CPU 不高。

3. ConcurrentHashMap 为什么是线程安全的？
• 底层结构：JDK 8 使用 Node 数组、链表和红黑树；不再采用 JDK 7 的 Segment 分段锁设计。
• 读操作：利用 volatile 读与内存可见性获取节点，通常不需要对整个桶加锁。
• 写操作：空桶优先通过 CAS 插入；冲突桶通过 synchronized 锁住桶头节点，降低锁粒度。
• 扩容扩容：通过 ForwardingNode 标识迁移中的桶，允许多个线程协助 transfer。
• 使用边界：单次 put、compute 等操作有相应并发保证，但“先 get 再 put”这样的组合操作不自动具备原子性。

4. JVM 发生频繁 Full GC，怎么排查？
• 确认现场：先看 GC 日志，确定收集器、Full GC 原因、触发频率、暂停时长和回收前后的堆占用。
• 判断类型：GC 后占用能显著下降，重点查对象分配与晋升过快、堆容量不足；GC 后仍居高不下，重点查长期存活对象或泄漏。
• 对象定位：结合对象直方图、Heap Dump 和 MAT 的 Dominator Tree、Retained Size、GC Roots 引用链定位占用源。
• 特殊原因：G1 还要看 Humongous 对象、Evacuation Failure、并发标记进度，以及显式 System.gc() 和 Metaspace 压力。

5. MySQL 的联合索引为什么能提升查询性能？
• 底层原理：联合索引是一棵按多个字段依次排序的 B+Tree，遵循最左前缀规则。
• 减少扫描：多个等值条件和合适的范围条件可以共同限定索引区间，避免扫描大量无关记录。
• 减少排序：当过滤条件和 ORDER BY 与索引顺序匹配时，可以利用索引的有序性，减少额外排序。
• 减少回表：查询字段全部由索引覆盖时，可直接返回结果；某些剩余条件还可利用 ICP 提前过滤。
• 设计原则：根据真实 WHERE、ORDER BY、覆盖需求确定列顺序，同时考虑索引大小和写入维护成本。

6. 一条 SQL 明明有索引，为什么可能不走？
• 优化器选择：优化器比较执行成本；低区分度、大比例数据命中或回表代价高时，可能主动选择全表扫描。
• 无法有效定位：不符合联合索引最左前缀，或在索引列上使用函数、表达式、某些隐式类型转换。
• 条件限制：LIKE 以 % 开头、部分 OR 组合，可能使索引难以有效缩小扫描范围。
• 统计信息：统计信息过旧或估算不准，可能造成执行计划选择失误。
• 排查方法：用 EXPLAIN / EXPLAIN ANALYZE 查看 key、type、rows、实际扫描量，再结合索引定义和查询条件定位。

7. MySQL 死锁一般是怎么产生的？你了解到的锁有哪些？
• 死锁本质：多个事务形成循环等待：事务 A 持有资源 X 等待 Y，而事务 B 持有 Y 等待 X。
• 常见原因：不同事务以相反顺序更新多条记录，或范围扫描、二级索引维护产生交叉加锁。
• 常见锁：按模式有共享锁 S、排他锁 X；InnoDB 还包括意向锁 IS/IX、记录锁 Record Lock、间隙锁 Gap Lock、临键锁 Next-Key Lock 等。
• 排查优化：查看 SHOW ENGINE INNODB STATUS 的死锁日志，明确持有锁与等待锁；统一加锁顺序、缩短事务并优化索引。

8. Redis AOF 的完整写入流程是什么？
• 写入起点：Redis 执行写命令并修改内存数据后，把需要持久化的命令追加到 AOF Buffer。
• 写入文件：在事件循环的合适阶段调用 write()，将数据写到 AOF 文件对应的操作系统 Page Cache。
• 真正落盘：write() 成功不等于持久化完成；fsync / fdatasync 才要求把文件相关的脏页同步到存储设备。
• 三种策略：appendfsync always 更可靠但开销大；everysec 通常每秒同步；no 主要由操作系统决定刷盘时机。
• 版本细节：Redis 7 以后采用多文件 AOF，通常由基础文件和增量文件共同组成。

9. Redis 主从复制中，复制积压缓冲区有什么作用？
• 核心作用：Replication Backlog 保存主节点近期产生的复制流，用于从节点断线后进行部分重同步。
• 判断依据：从节点重连时发送 replication ID 与 offset，主节点判断缺失区间是否仍在 backlog 中。
• 恢复方式：如果历史数据仍在，就通过 PSYNC 补齐；若已被环形缓冲区覆盖，则需要全量同步。
• 区别于 AOF：AOF Buffer 面向磁盘持久化，复制积压缓冲区面向断线续传；在线从节点的输出缓冲区则负责待发送数据。

10. Kafka 如何保证消息可靠传递？
• Producer：使用可靠确认与失败重试；幂等生产通过 PID 和序列号，避免同一生产者的重试造成重复写入。
• Broker：通过 Partition 多副本、ISR、副本确认和安全的 Leader 选举降低单节点故障造成的数据丢失风险。
• Consumer：通常先完成业务处理，再提交 Offset，实现至少一次消费；重复消费依靠业务幂等消除副作用。
• 事务语义：Kafka-to-Kafka 场景可用事务把输出消息与输入 Offset 原子提交；外部 MySQL 操作仍需额外一致性方案。

11. Kafka 消息大量堆积，你有什么解决办法？（追问：增加 Consumer 为什么可能没用？）
• 先看分布：检查消费组 Lag、各 Partition 的堆积量和消费速率，判断是全面堆积还是少数热点分区。
• 定位瓶颈：排查慢 SQL、下游 RPC、消费线程阻塞、批处理不足、频繁 Rebalance 和消费异常重试。
• 优化路径：优先优化处理耗时、批量操作和下游容量；确实缺少分区并行度时，再评估扩 Partition 与 Consumer。
• 扩容边界：同一消费组中，一个 Partition 同时只分配给一个 Consumer；Consumer 数超过分区数不会继续提升并行度。
• 热点问题：即使总体分区很多，单个热点 Partition 仍可能拖慢进度，需要调整 Key 路由或业务拆分策略。

12. 如何保证 MySQL 更新和 Kafka 发消息的一致性？（看你简历里面提到，这一块是如何做的？）
• 问题根源：数据库提交与 Kafka 发送属于两个独立系统，直接双写存在“数据库成功、消息失败”的故障窗口。
• Outbox 方案：在同一个 MySQL 本地事务中同时提交业务数据和 Outbox 消息记录，保证两者原子落库。
• 可靠投递：后台任务或 CDC 读取 Outbox，发送 Kafka，获得确认后更新投递状态；失败时持续重试。
• 处理重复：发送确认丢失时可能重复投递，因此生产端要有稳定消息 ID，消费端按业务键或消息 ID 幂等处理。
• 一致性边界：Outbox 保证最终一致，不是数据库与 Kafka 的分布式原子事务；还需监控积压、失败重试与告警。

13. 接口 RT 突然升高，但 CPU 很低，怎么排查？
• 先定位链路：结合 Trace 与 P95/P99 监控，先明确耗时增加发生在哪个接口、实例或下游调用。
• 查线程状态：连续抓取线程栈，检查 Socket 读取、锁等待、Future.join、线程池排队和数据库连接池等待。
• 查资源瓶颈：观察 MySQL 慢 SQL、Redis 延迟、RPC 超时、连接池 pending、网络重传和 DNS 解析耗时。
• 注意区别：CPU 低通常是线程在等待，不代表系统没有瓶颈；还要排除限流、排队和线程池规模过小。
• 治理思路：定位根因后再做超时、隔离、限流、批处理或扩容，不要直接盲目增加线程数。

14. select、poll、epoll 的核心区别是什么？（追问：为什么 epoll 适合高并发连接？LT 和 ET 又分别适合什么场景？）
• select / poll：两者都需在每次等待时遍历关注的文件描述符；select 使用固定大小的 fd 集合，poll 使用数组结构。
• epoll：先注册 fd，再从内核获得就绪事件，避免每次重新传入并遍历所有关注的 fd。
• 高并发优势：大量连接中只有少数活跃时，epoll 可显著降低无效扫描和重复拷贝开销。
• LT 水平触发：只要 fd 仍可读或可写，就会继续通知；实现简单，不易遗漏事件。
• ET 边缘触发：通常只在就绪状态变化时通知；需要非阻塞 IO，并持续读写直到返回 EAGAIN。

15. Agent 执行过程中出现死循环、反复调用同一个工具，应该如何检测和终止？
• 设置硬预算：限制最大执行步数、模型调用次数、工具调用次数、运行时长与 Token 消耗。
• 检测重复：记录 action、工具名、参数、结果和状态摘要，识别相同调用反复出现以及状态长期无法推进。
• 避免误判：合法重试与循环不同，需结合任务进展、错误类型、参数变化和可恢复性共同判断。
• 纠偏终止：触发阈值后可改写计划、替换策略、请求澄清；仍无法推进则有界终止并返回明确原因。
• 保留证据：记录终止原因、调用轨迹、预算与失败状态，方便线上复盘和自动化评测。

16. 一个 Agent 执行到一半服务重启，如何从 Checkpoint 恢复，并避免已经完成的步骤被重复执行？
• 保存状态：在关键节点持久化 Checkpoint：任务目标、执行状态、上下文、已完成步骤、工具结果和剩余预算。
• 恢复执行：重启后加载最近的一致性 Checkpoint，恢复状态机，只调度尚未完成的步骤。
• 副作用防重：为发消息、写数据库等工具调用生成稳定的 operation ID，并在 Tool Ledger 中记录状态与结果。
• 处理不确定态：若工具执行后服务崩溃、结果未落账，先查询外部操作结果；下游需支持幂等键或状态核对。
• 核心边界：Checkpoint 解决状态恢复，Tool Ledger 与下游幂等解决重复副作用；单靠保存进度无法保证恰好执行一次。
