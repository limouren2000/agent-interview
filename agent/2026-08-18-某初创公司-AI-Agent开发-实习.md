某初创公司｜AI-Agent开发岗面经

最近面了某初创公司的 Agent 开发岗，岗位偏 AI Agent 工程与后端实现。没有八股，面试官几乎全程围绕我的 CLI Agent 项目往下追，重点看我是否真正理解 Agent 的运行机制，以及能不能把一个 Demo 做成可靠的工程系统。

把这次问到的问题整理一下，给准备 AI Agent、Go 后端转 Agent 开发方向的朋友参考。

CLI Agent 项目拷打
先介绍一下你的 CLI Agent，它解决了什么问题？
为什么选择 CLI 形态，没有选择 Web 或 IDE 插件？
从用户输入一条任务开始，整个执行链路怎么走？
模型、提示词、工具注册、Agent Loop 和会话存储分别放在哪一层？
Agent 怎样读取项目代码，又怎样判断哪些文件与任务相关？
工具返回几千行日志时，你怎么避免上下文被撑爆？
模型选择了错误工具，系统会怎样处理？
命令执行超时、进程卡死或用户主动取消时，怎样停止任务？
Agent 修改错文件以后，有没有回滚机制？
怎样限制文件读取范围和 Shell 命令权限？
如果模型连续重复同一个动作，系统如何判断它进入了死循环？
项目做过哪些评测？怎么证明修改后效果真的提升了？
这个项目里哪些代码由你独立完成，哪些部分使用了 AI 辅助？
如果明天更换模型，你的 Agent 架构需要修改多少？

Skills 怎么做
面试官：你用过 Skills 吗？有没有自己设计过 Skill？
继续追问：一个 Skill 应该包含什么？模型什么时候加载？多个 Skill 同时命中怎么办？Skill 执行失败后怎么恢复？你怎样测试一个 Skill 是否有效？
我的理解是，Skill 可以看成一份可按需加载的任务能力包。它至少需要包含清晰的名称与描述、适用和禁用场景、主体流程、输入输出约束、失败处理，以及完成任务所需的脚本、模板和参考资料。
Skill 的价值在于把团队经验沉淀成可复用的执行流程。设计时最重要的部分是触发边界。如果描述过泛，很多无关任务也会加载；如果描述过窄，用户稍微换一种表述就无法命中。加载后还要有明确的验证标准，不能只告诉模型“应该怎样做”，还要规定完成后检查什么。
我会采用渐进式加载：平时只向模型暴露名称和简短描述，命中后再加载完整流程，执行到具体环节时才读取脚本、模板或参考资料。这样可以控制上下文，也能减少不同 Skill 之间的干扰。

MCP 怎么做
面试官：你用过 MCP 吗？有没有自己开发过 MCP Server？
继续追问：MCP Server 如何定义工具？客户端和服务端怎样通信？工具调用超时怎么办？权限放在哪一层控制？服务断开以后怎样恢复？为什么不用普通 HTTP API？
回答这部分时，我会先讲清 MCP Client、MCP Server 和底层业务服务之间的关系。MCP Server 负责向 Agent 暴露工具、资源和提示能力，业务数据与真实操作仍然需要进入已有的数据库、内部 API 或服务系统。
如果让我实现一个 MCP Server，我会重点处理工具 Schema、参数校验、身份认证、超时取消、错误分类、幂等、审计日志和权限隔离。模型产生工具调用只能代表调用意图，服务端仍然需要按照普通后端系统的安全标准重新校验。

MCP 和 Skills 有什么区别
Skills 更偏任务经验与执行方法，解决“遇到这类任务应该怎样完成”；MCP 更偏标准化能力连接，解决“Agent 怎样发现并调用外部工具或数据”。
一个代码审查 Skill 可以规定先检查变更范围，再执行测试，随后分析安全风险并输出报告。真正读取仓库、运行测试和查询漏洞库的动作，可以由内置工具、CLI 或 MCP Server 完成。
两者可以组合使用：Skill 负责流程编排和经验约束，MCP 负责连接外部能力。拥有很多 MCP 工具，并不代表 Agent 会正确完成任务；写了很长的 Skill，也无法凭空获得数据库和外部系统的操作能力。

Agent Loop 有什么用
面试官：Agent Loop 和普通模型调用有什么区别？什么时候结束？工具失败后是否继续？怎样避免无限循环？
Agent Loop 的基本流程是模型观察当前状态、决定下一步动作，系统执行工具，再把结果交回模型继续判断。这个过程会持续多轮，直到任务完成、达到最大步数、发生不可恢复错误，或者用户主动终止。
Loop 的工程难点集中在退出条件、错误恢复、重复动作检测、Token 预算和人工审批。模型说“完成了”只能作为结束信号之一，系统还需要检查文件是否真的修改、命令是否成功、测试是否通过，以及当前目标是否已经满足。

什么是 Deep Agent
面试官：听说过 Deep Agent 吗？它和普通 Agent 有什么区别？
我会先确认面试官指的是通用概念，还是 LangChain 的 Deep Agents 框架。在当前 Agent 语境里，Deep Agent 通常面向长周期、多步骤任务，强调任务规划、上下文管理、文件系统、子 Agent、长期记忆、沙箱和人工审批。
普通 Agent 可以依靠一次简单的 ReAct Loop 完成短任务；Deep Agent 需要把复杂目标拆解成多个阶段，把大体量信息转移到文件或外部存储，并将独立子任务交给隔离上下文的子 Agent。这里的“Deep”更多表示任务执行深度和工程能力完整度，与单纯增加推理 Token 没有直接等号。

你知道 OPC 吗
面试官：知道 OPC 吗？有没有接触过？
如果放在当前 AI 创业语境中，OPC 通常指 One Person Company，也就是由一名核心个体主导，通过 AI Agent、自动化工具、软件和内容杠杆完成过去需要小团队承担的工作。
我对 OPC 的看法是，AI 可以显著降低产品开发、内容生产、客服和运营成本，但一个人仍然需要承担需求判断、获客、交付、风险和最终责任。OPC 真正考验的是能不能建立可重复运行的业务系统，而非同时打开很多 AI 工具。
我目前更多是通过个人项目接触这种工作方式：用 AI 辅助需求拆解、写代码、测试、复盘和内容生产。它已经改变了个人的工作效率，但距离稳定经营一家公司，还要补齐客户、收入和持续交付能力。

你知道 FDE 吗
面试官：了解 FDE 吗？说说你的看法。
FDE 通常指 Forward Deployed Engineer。这个角色会深入客户现场或业务环境，理解模糊需求，把模型、Agent、数据和现有系统连接起来，快速完成原型、部署和后续迭代。
AI 产品演示越来越容易，真正困难的环节集中在业务理解、数据接入、权限、安全、评测和稳定交付。FDE 需要同时具备工程能力、产品判断、沟通能力和结果意识。对 Agent 公司来说，这类角色负责缩短模型能力与客户真实流程之间的距离。
我觉得 Agent 开发岗未来会逐渐出现两条路线：一条深入平台、模型调用、工具系统和 Agent Runtime；另一条更接近 FDE，直接围绕客户问题完成端到端交付。Go 后端的工程基础在两条路线里都有价值。

反问环节
公司当前主要做通用 Agent，还是垂直业务 Agent？
开发岗需要直接参与客户需求和交付吗？
团队如何评测 Agent 效果？有没有固定的 Evals 和回归集？
项目中 Skills、MCP 和自研工具分别承担什么角色？
公司内部使用哪些 AI 编程工具？生成代码怎样评审和进入生产环境？
这个岗位未来更偏 Agent 平台工程，还是 FDE 式交付？

今日求职复盘
这场面试给我最大的感受是：求职是一场关于能力、信任、结果和分工效率的交易。公司关注的是把某项责任交给你以后，未来产生的价值能否覆盖工资、管理和失败成本。
技术能力只是判断的一部分。公司还会观察你能否稳定交付、能否理解业务约束、出现问题时是否可信，以及需要投入多少管理成本。简历和面试的核心作用，就是用证据降低这些不确定性。
比“我熟悉 Agent、Skills 和 MCP”更有说服力的表达是：我处理过什么真实问题，当时有哪些限制，我采取了什么行动，得到了什么可验证结果，这套经验怎样迁移到你们的岗位。
海投最大的问题，是同一份简历面对完全不同的岗位，项目表达也缺少重点。更有效的方式是选择一个清晰的岗位簇，围绕该岗位准备对应项目、案例和回答，让面试官快速看见你在当前问题上的比较优势。
