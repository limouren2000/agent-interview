1. 你的 Agent 项目整体架构是什么？
• 我会把整体分成三层：接入层、Harness / Runtime 层、业务应用层。
• 接入层负责会话接入、SSE 输出、用户身份、请求追踪、上下文组装。
• Harness / Runtime 层是核心：包含意图识别、规划、Agent Loop、工具编排、RAG、记忆、策略控制、校验器、恢复机制和观测日志。
• 业务应用层负责对接具体场景能力，比如新闻检索、资讯分析、研究档案、业务 API 和知识库。
• 如果按执行链路讲，就是：用户请求进入 → 意图识别与目标结构化 → 判断直接回答 / RAG / 工具调用 → Loop 执行 → validator / repair 校验 → SSE 流式返回结果。
• 我会强调这不是把模型直接包起来，而是用 Harness 把模型、工具、状态、策略和恢复能力组织成一个可控系统。
• 核心目标是：可嵌入、可恢复、可评测、可审计，而不是只做一个能跑通 Demo 的 Agent。

2. 你如何划分模型与工程系统的边界？
• 我的理解是：模型负责概率推理，工程系统负责确定性的约束。
• 模型更适合做意图理解、改写、规划候选生成、自然语言回答和不确定任务的推理。
• 工程系统负责权限、状态管理、工具注册、参数校验、超时重试、幂等控制、预算限制、审计日志和失败恢复。
• 也就是说，模型可以提出“怎么做”，但不能绕过系统直接“随便做”。
• 在我的项目里，Harness 就是这条边界：模型输出不会直接落地，而是必须经过 policy、schema 校验、validator 和 repair。
• 对高风险行为，工程系统必须比模型更强势，例如写操作、敏感查询、外部副作用工具，都要由系统显式批准。
• 我会把这件事概括成一句话：让模型负责智能，让系统负责可靠。

3. 你如何设计的工具注册？工具的输入 Schema、输出 Schema、超时、重试、权限和错误码如何定义？
• 我会把工具注册设计成统一 ToolSpec，而不是每个工具各写一套逻辑。
• ToolSpec 至少包含：name、description、input_schema、output_schema、timeout、retry_policy、permission、idempotency、error_codes。
• 输入 Schema 用结构化字段定义参数类型、是否必填、默认值、枚举值和字段解释，避免模型自由拼参数。
• 输出 Schema 也要标准化，约定 success、data、error、metadata 这些字段，方便后续节点稳定消费。
• 超时要按工具类型分层：本地轻工具短超时，网络 I/O 中超时，重查询或异步任务更长，但都必须可配置。
• 重试不能一刀切。只对幂等、瞬时故障类错误做有限重试；对参数错误、权限错误、业务拒绝不重试。
• 权限要做分级，例如只读、写入、高危三类；高危工具还要加人工确认、白名单或双重校验。
• 错误码要分层：参数类、权限类、超时类、网络类、依赖类、业务类、系统类，便于模型与系统分别处理。
• 这样做的价值是：工具能被稳定调用、可观测、可演进，也方便灰度和评测。

4. 你是如何实现完整的 Agent Loop？用到了第三方框架了吗？
• 我的 Agent Loop 是自己实现的，没有把核心执行链路交给第三方框架。
• 一个完整循环通常是：读取当前状态 → 调用模型做决策 → 产出 action / response → 若要调工具则执行工具 → 写回观察结果 → 再进入下一轮。
• Loop 内我会维护显式状态，包括当前目标、已完成步骤、工具调用历史、中间证据、预算消耗和停止条件。
• 每一轮都要经过校验：是否合法调用工具、参数是否完整、是否违反策略、是否进入重复动作。
• 如果模型回答可以直接结束，就进入 finalize；如果工具失败，就根据错误类型决定 repair、重试、澄清或降级。
• 我还会在 Loop 外面补上 checkpoint / resume，让服务重启后可以继续执行，而不是整段重来。
• 第三方框架我了解，比如 LangGraph，但我的项目目前更强调自己掌控状态机、协议和恢复机制，所以没有直接接入。

5. 在你这个场景下，如果 Agent 连续调用工具停不下来，你会如何检测并终止死循环，同时避免误伤正常的长任务？
• 我会先区分“正常长任务”和“无效循环”，不能只看轮次多就直接杀掉。
• 检测维度一般有四类：重复动作、低信息增益、状态不前进、预算异常消耗。
- 重复动作指连续调用同一个工具、相同参数、得到相似结果；
- 低信息增益指多轮之后证据没有新增；
- 状态不前进指目标没有推进、同一个槽位反复修补；
- 预算异常就是 token、工具次数、耗时持续上涨。
• 我会给每轮执行打 progress signal，比如新增证据数、完成子任务数、置信度变化、未决问题数量。
• 如果连续多轮 progress 很低，就触发 early stop，而不是等到硬上限。
• 为了避免误伤正常长任务，我会设置“白名单型长任务条件”，例如正在遍历多个对象、分页查询、批量处理，这类任务虽然轮次多，但状态在持续前进。
• 终止方式也分层：先澄清、再降级、再安全终止；而不是直接把任务砍掉。
• 本质上是用“进度感知 + 预算控制 + 重复检测”三件事一起判断。

6. RAG 中出现召回错误、漏召回或召回内容冲突时，你如何定位问题的？
• 我一般按链路拆开排查：query、召回、重排、切片、上下文构造、最终回答。
• 先看 query 是否有问题：
- 用户原问题是否模糊，是否需要 rewrite，是否缺少约束词。
• 再看召回层：
- 稀疏召回有没有命中，向量召回相似度是否合理，topK 是否过小，过滤条件是否过严。
• 漏召回很多时候不是模型问题，而是切片策略、索引构建、元数据过滤或 chunk 粒度不合适。
• 如果出现内容冲突，我会检查来源是否版本不同、时间不同、文档质量不同，以及 reranker 是否把低质量片段排到了前面。
• 最后再看答案生成阶段：
- 模型有没有正确引用证据，是否把冲突信息混成一句话。
• 为了能定位，我会记录每一步中间结果，例如 query rewrite 后的查询词、召回候选、rerank 分数、最终引用片段。
• 这样 badcase 回放时就能知道问题到底出在检索、排序，还是出在生成。

7. 为什么要把策略、工具、模型和提示词配置化？配置变更如何做到版本管理、灰度发布与快速回滚？
• 配置化的核心目的，是把变化频繁的内容从代码里解耦出来，提高可维护性和可运营性。
• 策略配置化后，可以快速调整预算、权限、阈值和拦截规则，而不用每次发版。
• 工具配置化后，可以方便增删工具、改超时、改重试、改路由，不影响核心框架。
• 模型与提示词配置化后，可以按场景切换不同模型、不同 prompt 模板，便于做 A/B test 和效果评估。
• 版本管理上，我会给每次配置变更分配 version，并保存变更人、时间、diff 和生效范围。
• 灰度发布时，不会全量生效，而是按用户、租户、流量比例或业务场景逐步放量。
• 如果观察到成功率下降、延时变差或坏例增多，就能基于版本号快速回滚到上一个稳定版本。
• 这样做能让 Agent 系统既像工程系统一样稳，又像产品系统一样灵活。

8. 预先配置工具与让模型自主选择工具有什么区别？在新闻解读场景中你会选择哪一种，为什么？
• 预先配置工具，指系统先根据任务类型决定可用工具集合，模型只在一个受控范围内行动。
• 模型自主选工具，则是把选择权更多交给模型，让它决定何时查新闻、何时查知识库、何时调用分析工具。
• 前者优点是可控、稳定、好治理；缺点是灵活性略弱。后者优点是更灵活，但更容易误用工具或走偏。
• 在新闻解读场景里，我更倾向“受控自主”：先由系统限定工具范围，再让模型在这个范围内选择。
• 原因是新闻解读既需要一定灵活性，又非常依赖时效性、来源可信度和预算控制。
• 如果完全放开，模型可能无意义地多次搜索、重复抓取，甚至引用不稳定来源。
• 所以我会先做场景路由，再开放新闻检索、资讯聚合、知识库、总结工具等少量工具给模型使用。
• 这样能在灵活性和可控性之间取得平衡。

9. 多条提示词顺序执行时，如何把上一阶段的结果可靠地传递给下一阶段？怎样避免错误逐级放大？
• 我不会只靠自然语言把上一阶段结果“口头传递”给下一阶段，而是尽量结构化传递。
• 更稳的做法是每一阶段产出明确的中间结果对象，例如 goal、plan、retrieval_result、tool_result、final_answer。
• 这些结果要配套 Schema 校验，保证字段完整、类型正确、关键约束不丢失。
• 进入下一阶段前，我会做 validator，检查上一阶段结果是否满足下游输入要求。
• 为了避免错误逐级放大，可以在关键节点加 double-check，例如摘要后回看原文、规划后检查是否遗漏约束、回答前核对引用。
• 对低置信度结果，不直接传给下一阶段，而是回退修复、澄清或降级。
• 另外要保留原始证据，不要只传“压缩后的一句话结论”，否则后续容易被错误结论带偏。
• 本质上是：结构化传递 + 节点校验 + 必要时回退，而不是串行放大错误。

10. 讲讲 LangGraph 里面的基本概念
• LangGraph 可以理解成一种面向 Agent 的状态图编排框架，核心思想是“显式状态 + 节点执行 + 边控制流”。
• State 就是全局状态，保存上下文、历史消息、中间结果和控制字段。
• Node 是执行单元，一个节点可以是模型调用、工具调用、检索、校验或普通函数。
• Edge 是节点之间的连线，表示下一步流向；Conditional Edge 则根据状态决定分支。
• Reducer 用来定义状态合并方式，尤其是在并行分支回写状态时很重要。
• Checkpointer 用来持久化执行状态，支持中断后恢复。
• Interrupt 可以在运行中暂停，适合人工介入或需要等待外部事件的场景。
• Store 一般用于更长期的状态或记忆存储。
• 所以它适合做复杂、多轮、可恢复的 Agent 工作流；只是我自己的项目目前没有直接接入它。

11. 单 Agent 与多 Agent 分别适合什么场景？主 Agent 如何拆分任务、选择子 Agent、汇总结果并处理子 Agent 幻觉？
• 单 Agent 更适合链路相对清晰、工具数量有限、任务复杂度中等的场景，系统简单、延时更低、治理更容易。
• 多 Agent 更适合任务异构、专业性分工明显、需要并行处理或需要不同角色协作的场景。
• 主 Agent 的第一步不是盲目拆分，而是先判断问题是否真的值得拆。简单问题不必多 Agent。
• 如果要拆分，通常按子任务类型拆，比如检索 Agent、分析 Agent、执行 Agent、校验 Agent。
• 选择子 Agent 时，我会根据任务需求、能力标签、成本和历史效果做路由，而不是固定写死。
• 汇总结果时，主 Agent 不能只拼接答案，而要做证据对齐、冲突消解、来源校验和最终裁决。
• 子 Agent 幻觉处理的关键，是不给它们过度自由：输入要受限、输出要结构化、结果要可回溯。
• 如果多个子 Agent 结论冲突，主 Agent 要求它们返回依据，再由 validator 或裁决节点统一判断。
• 所以多 Agent 的重点不只是“多”，而是分工、协议和汇总机制。

12. Agent 的短期记忆、长期记忆和工作记忆分别应该存什么？记忆冲突、过期和上下文污染如何处理？
• 我会把三种记忆分开看：工作记忆、短期记忆、长期记忆。
• 工作记忆是当前一次任务执行期内的临时状态，比如当前目标、计划、已完成步骤、中间工具结果。
• 短期记忆更偏会话级，保存最近几轮对话摘要、用户刚刚提供的偏好和最近上下文。
• 长期记忆保存跨会话仍然稳定有价值的信息，比如用户画像、长期偏好、明确确认过的事实。
• 记忆不能无条件写入，要先做写入门槛判断，确认信息是否稳定、是否高价值、是否经过验证。
• 记忆冲突时，不能简单覆盖，而要保留版本、时间戳、来源和置信度，必要时触发澄清。
• 过期问题要靠 TTL、衰减和定期清理解决，不同类型信息生命周期不同。
• 上下文污染主要来自错误写入和错误召回，所以要做隔离、审核、压缩和纠错回滚。
• 本质上，记忆系统不是“存得越多越好”，而是“写得准、取得对、忘得掉”。

13. 在哪种场景下，你认为 Agent 要利用到线程池？
• 线程池不是为了“看起来高级”，而是为了在有并发价值的地方稳定复用线程、控制资源。
• 第一类场景是 I/O 密集型并发，比如同时调用多个外部工具、并行检索多个数据源、并发抓取网页。
• 第二类场景是多路召回与并行评估，比如 BM25、向量检索、重排前候选收集可以并发执行。
• 第三类场景是多 Agent 或多子任务并行，例如一个负责检索、一个负责总结、一个负责校验。
• 第四类是后台异步任务，比如记忆写入、日志落盘、缓存刷新、低优先级摘要压缩。
• 但线程池不能滥用。CPU 密集推理、强顺序依赖任务或共享状态复杂的任务，不一定适合并发。
• 设计上要关注线程池大小、队列长度、拒绝策略、超时控制和上下文传播。
• 所以线程池更多是工程治理能力，不是 Agent 本身的智能能力。

14. SSE 流式输出的连接生命周期如何管理？
• SSE 生命周期一般包括：建立连接、持续推送、心跳保活、正常结束、异常断开和重连处理。
• 建立连接时要分配 request_id / session_id，并把当前执行状态绑定到这个流上。
• 推送过程中要区分事件类型，例如 token、tool_event、status、final、error，前端才能稳定消费。
• 为了防止中间代理或浏览器断开，要定期发送 heartbeat。
• 正常结束时要显式发送 final / done 事件，并释放相关资源。
• 异常断开时，后端要感知连接关闭，及时取消无意义的后续推理或工具调用，避免资源泄漏。
• 如果业务要求可恢复，可以配合 checkpoint 和 last_event_id 做断点续传或重新拉取结果。
• 另外还要控制连接数、超时时间、背压和慢客户端问题，避免大量 SSE 长连接拖垮服务。
• 所以 SSE 管理的关键不是“能流出来”，而是整个连接过程要可控、可清理、可恢复。
