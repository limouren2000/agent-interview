## 面经正文

常见问题见千问C端一面面经，分享两个很有价值的问题：
1. 推荐和搜索 Agent 联合训练，要不要共享参数？
面试官给了一个购物助手场景：先根据用户兴趣推荐商品，用户继续提需求后，再转成搜索、筛选。怎么搭建，又怎么优化？
我的回答：可以用主 Agent 分流，由推荐和搜索 Agent 分别处理，同时维护连续的用户兴趣信息。训练上，我倾向先分别提升两个模块的能力，再围绕最终业务目标联合优化。
面试官继续问：那联合训练时，两个 Agent 是共享一套模型参数，还是各用一套？
这一步回答的不好，当时确实没做过整个多 Agent 系统的联合训练，也没想清楚两种方案的取舍。
复盘补充：
首先要分清“角色分工”“共享用户状态”和“共享模型参数”。推荐、搜索是两个角色，也可以由同一个模型配不同指令来承担。
如果任务相近，我会先比较共享参数方案，观察能否复用能力；如果任务差异大，再比较独立参数或共享底座、独立适配器，同时检查任务之间是否互相干扰。共享与独立策略的取舍，也有针对多 Agent 工作流的研究讨论。
联合优化还要说清：轨迹怎么采样，奖励评价整条任务还是局部步骤，最终成败怎么归因到各角色。最后用效果、延迟和成本做对照，不能只回答“先分开训，再一起训”。
2. 线上回捞的回答，筛选后就适合做 SFT 吗？
我当时介绍了模型筛选加人工校验的数据流程。
面试官追问：旧模型的回答不一定够好，为什么不保留真实用户问题，让更强的教师模型重新回答？用户点击或转化，也不代表原回答就是最好的。
复盘补充：
应把“问题从哪来”和“训练答案从哪来”分开。真实问题帮助贴近线上分布，答案质量需要另外验证。
重新做，我会保留真实问题、必要历史和工具结果，让教师生成候选，再做规则校验和人工抽查，尤其检查有没有编造工具结果。同一批问题下，对照“筛选旧回答”和“教师重写后校验”两组数据，用训练后的评测结果判断收益。

另外还问了离线指标如何对应线上价值、首字延迟与完整回复耗时。

算法题是岛屿数量。
