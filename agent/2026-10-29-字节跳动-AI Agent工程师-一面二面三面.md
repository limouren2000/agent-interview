今年 5—7 月份大概三个月的时间，出去面试了一圈，一是看看有没有好机会，二是也看看自己掌握的知识是不是过时。面试了字节（2 次）、大疆、B 站、小红书、阿里以及蚂蚁等叫得上名号的大公司，也聊了遥望科技以及 OKX这些规模较小的公司。最终拿下字节和大疆的两个 offer，不过因为不是太匹配，都没去。接下来在这个号上我会分享我的一些面试经历和感受，欢迎追更。
面了这么多轮，我说说整体的一些面试心得。其实我作为面试官，也经常面试别人。在接受别人面试的时候，我通常会遵守一套流程规则，今天分享出来，希望对你有用：

1. 随时准备面试。 倒不是一定要出去，而是在 AI 技术日新月异的今天，一定要去试试自己对这些技术的掌握是否过硬，方式要么通过面试，要么去创业，而非自己一直感觉良好。
2. 不要内耗。 面完了要总结，要复盘，但是不要内耗、否定自己。完全没必要，不是你不行，只是不合适而已。不合适体现在多方面，甚至就是面试官觉得你的热情不足。
此外，有可能是“虚岗”，就是这个岗位并不存在。别怀疑，我就经历过。
3. 你写在简历上的每一句话，你在面试问答过程中的每一句话，都是靶子，都可能成为面试官问题的目标。 所以写的时候慎重一些。一定要确保你写的项目是你真实经历过的，技术深度起码要考虑到三层，才能经得住问，做面试的包装也是如此。

举例来说，你说经过你的努力，某个指标达到了70%，那面试官往往会问三个问题：你做了什么达到这个指标？核心难点是什么，怎么克服？剩余30% 为什么没达成，如果再次设计，你会怎么做？这几个问题，建议大家可以对着简历去问一问。
4. 面试是双向挑选，而非单向筛查。 不需要那么自卑或者小心翼翼。看见不对劲的面试官一定要跑，不要委屈自己。
为了便于大家对标和体验，我再说下我的工作情况。在我公众号的第一篇其实已经说过，现在在某大厂工作，职级对标 P8，主要的方向是 AI Agent 工程开发，负责企业内部的 Agent 平台研发工作。还有个关键因素，目前已经 38 岁，年龄是个不得不考虑的因素。

我当时面的岗位是做 toB 端 Agent 平台的，具体的岗位保密。第一轮面试的结果是通过。

问题 00
自我介绍，以及目前主要负责的工作
我： 我按照简历介绍了个人经历，具体内容在这里略去。目前主要负责 AI Agent 平台的研发工作，担任 TL。

问题 01
这个平台的产品定位是什么？
我： 平台主要围绕 Agent 的生命周期展开，提供开发、上线和运行维护所需的配套能力。
开发者完成 Agent 开发后，还需要将其上线。在企业内部，这个过程涉及权限体系接入；上线后，则需要保障运行稳定，并提供错误排查和处理能力。
整体上，平台由相关功能组件，以及围绕 Agent 运行引擎构建的产品组件组成。
问题 02
能介绍一下平台的基础架构吗？
我： 平台支持三种构建和运行方式：低代码、高代码和托管。
低代码包含两种模式。一种是传统的工作流，用户通过拖拽节点，配置输入输出和条件分支，完成流程编排。

另一种由大模型决定执行过程：接收用户问题后，选择需要调用的工具，将执行结果补充到上下文，再决定下一步操作或结束任务。工具、知识等能力通过配置接入。
高代码面向开发者。开发者在本地编写上下文处理逻辑和工具，提交后由平台托管运行。
第三种是提供独立的远程执行环境。用户提交任务后，Agent 在该环境中运行，完成后取出产物。这种方式比较适合需要长时间执行的任务。
围绕这些能力，平台还需要提供身份权限、运行隔离、动态扩缩容，以及执行过程的记录和调试能力。
问题 03
平台在技术上有哪些难点？
我： 对我来说，主要难点是如何在无状态的 Web 服务中支持有状态的 Agent 任务。
例如，多轮对话需要保留历史上下文，将其与当前输入结合，才能准确理解用户意图。需要人工参与的任务，同样需要保存执行状态。

我的思路是将用户相关的状态外置到持久化存储中，降低执行实例对本地状态的依赖，便于扩缩容。
持久化的内容包括工具输入输出、执行过程中的上下文等，再通过会话标识将这些记录关联起来。
问题 04
你提到了公开评测和 Text-to-SQL 两项经历，能展开介绍吗？
我： 我先介绍公开评测这部分。我们的优化主要从实际遇到的问题出发。
首先引入一套评测集，作为后续版本迭代的衡量标准，再逐步调整方案。
最初遇到的明显问题，是任务经常在执行过程中中断。例如，模型输出的 JSON 多了或少了一个符号，就可能导致解析失败。

一开始采用的是重试，但单纯重试不一定能修正错误。后来，我们把错误信息反馈到 Agent 的执行循环中，让模型结合错误判断后续如何处理。对于缺少密钥这类问题，重复执行并不能解决。
第二个问题是上下文超限。对于较长的 PDF 内容或搜索结果，我们将其放到外部存储中，并告知 Agent 存储位置，需要时再通过工具读取。
在此基础上，仍然需要压缩上下文。压缩时要保留用户的原始问题、近期必要的对话和任务进度。我们遇到过原始问题被压缩掉的情况，导致 Agent 持续循环，却无法给出有效结果。
接下来遇到的问题是，任务虽然能够完成，但产物不一定符合要求。
例如，在生成网页的任务中，Agent 启动服务后，通过 curl 获得 200 状态码，就判断网页已经完成。但实际上，页面可能并没有生成需要的内容。

任务拆分也存在类似问题。有时计划只有“生成网页”和“检查网页”两步，没有进一步明确用户意图、页面内容、样式，以及是否需要收集资料，难以指导具体执行。
因此，后续调整主要包括细化任务计划，以及检查实际产物。以网页为例，需要在浏览器中打开页面，确认内容和样式是否符合要求。
此外，也针对部分评测题引入过专项工具。这类优化更依赖特定题型，相比上下文处理等通用能力，硬编码的成分会更多一些。
问题 05
公开评测中的优化，与实际生产使用有哪些冲突？
我： 主要有两方面。
一是工具的适用性。针对特定评测题引入的工具，在日常办公任务中未必适用。Agent 可能在不需要使用这些工具时仍然调用它们，导致整体耗时增加。

二是评判标准不同。部分评测题可以直接判断答案是否正确，但 PPT、网页这类产物，很难仅用对错评价，还需要考虑内容、呈现效果和整体质量。
这些差异无法完全通过榜单体现。因此，我们也采用过人工标注的方式，对生成的 PPT 进行评分。
问题 06
有没有改动之后，效果反而下降的案例？
我： 有一次引入反思工具的经历比较典型。当时主要想解决三类问题：任务偏离目标、对产物完成情况的判断不准确，以及工具调用陷入循环。
例如，要求生成 PDF，最终却生成了 PPT；或者仅凭 curl 返回 200，就认为网页已经完成。
引入反思工具后，任务耗时明显增加。Agent 将大量时间用于自我检查和反复调整计划，任务成功率反而下降。

因此，我们回滚了这次改动，恢复到原来的版本，随后继续寻找更轻量的方案，希望在解决问题的同时减少额外开销。
问题 07
你会怎么形容自己的管理风格？
我： 略，这个感觉就自由发挥吧，非技术问题。
问题 08
AI coding 的比例越来越高，从管理上看，你觉得带来哪些改变或者挑战？
我： 我先讲挑战。我觉得最大的挑战，就是如何衡量产出，做得好还是不好。不只是 AI Coding，还有文档这些...其他内容略去。
大概是这些思考。

这次面试的复盘
平台定位这道题答得有点绕。先拿产品和框架类比，后来才说到平台具体做什么。这一段可以直接一点。
“随便它怎么扩缩容都可以”，这句说得太满。状态存到外部以后，工具执行到一半怎么办、重复执行怎么办，还得继续考虑。“Web 无状态”这个说法也不够准确。
评测那一段讲得有点长。错误处理、上下文、计划、检查，都挤在一起。下次可以先讲一个具体的问题，对方想了解其他的，再往下展开。

简单交代一下背景：我目前在某大厂做 AI Agent 平台研发，之前也做过自然语言查询和数据分析相关的工作。面试的岗位是 toB 方向，和数据、Agent 都有关，具体团队就不展开了。

面试问答
问题 00
先介绍一下经历。你在这些项目里具体负责什么？
我： 我的工作主要围绕数据分析和 AI Agent 展开。早期负责自然语言查询，让用户用自然语言向数据提问。当时还没有大模型，主要依靠语法、语义识别等方式实现。
追问： 你负责的是自然语言查询这个产品，还是数据平台本身？

我： 主要是自然语言查询，其他部分参与得不多。后来开始结合大模型做数据分析助手，我负责推进这个项目，参与工程架构设计、模型优化，以及上线后的反馈收集。
再往后，做过 Agent 开发平台、Text-to-SQL 工具和通用任务智能体。目前主要负责 Agent 上线运行所需的平台能力，包括运行维护、问题排查和扩缩容等。
问题 01
哪个项目做得比较好，可以深入聊聊？
我： 我更想讲通用任务智能体。Text-to-SQL 的评测工作在当时有一定价值，但随着模型能力提高，现在再回头看，一些做法已经没有那么多可讲的内容了。通用任务智能体里遇到的工程问题，到今天还有参考价值。
追问： 两个项目都聊一下。Text-to-SQL 当时主要是为了参加评测吗？
问题 02

我： 有对外和对内两方面考虑。一方面是通过评测了解技术水平；另一方面，当时也需要一个好用的自然语言查询工具。最终还是希望把它接入 Agent 平台，让用户在实际任务中使用。
实际使用效果怎么样？这个准确率对应的可用性如何？
我： 实际效果很依赖数据治理和业务知识准备。数据整理得是否充分、相关知识是否完整，都会影响查询效果。
使用上，它作为一个工具接入 Agent。需要查询数据时，可以配置到工作流里，也可以交给模型决定是否调用。
追问： 放进具体流程里，准确性要求应该很高。你说的这个准确率，可用性到底怎么样？我还不太有概念。
我： 先说统计口径。我们会定期抽取线上查询，由熟悉 SQL 的同事检查，判断生成的 SQL 是否有问题。用户实际使用后反馈的错误，也会作为失败案例纳入统计。

问题 03
为了提高 Text-to-SQL 的准确率，你做了哪些关键工作？
我： 我把它分成技术和非技术两部分。当时我觉得，数据和知识的治理，甚至比模型侧的调整更关键。
数据治理首先要看用户通常问什么，再对应到表和字段，检查空值、异常值等问题。同时还要考虑查询性能，有些分析不能每次都从底层明细数据重新计算，需要提前整理成适合查询的数据。
追问： 这些清洗是什么时候做的？是根据之前的查询来清洗吗？
我： 这里有两件事。清洗通过定时任务执行；用户查询的反馈是另一条流程。用来发现失败案例，再判断需要调整哪些清洗规则。
规则调整以后，放进后续的清洗任务里执行，整理出来的数据再作为后面分析的基础。
追问： 每接入一个业务场景，都要做这样的整理？

我： 是的，需要结合具体业务做数据和知识的整理。
问题 04
如果放到现在来看，有什么新的做法？
我： 我会让 Agent 承担更多失败案例分析和数据清洗的工作。
例如，给它提供查询工具和失败案例，让它逐条检查空值、异常内容、编码问题，把需要处理的内容找出来，再接入后续清洗流程。我觉得这部分可以交给 Agent 做更多事情。
问题 05
字段含义和业务知识怎么理解？有没有比较通用的知识整理方法？
我： 除了数据本身，还需要整理字段含义和业务语义。同样是一个 ID，不同字段可能代表不同对象；用户习惯使用的业务简称，也不一定能直接对应到表里的字段。

这些知识一部分来自用户反馈，另一部分来自已有文档和业务知识系统。有些信息会随时间变化，仅靠固定文档不够，还需要查询对应的信息来源，再参与后面的解析和 SQL 生成。
追问： 除了这些特殊场景，有没有比较通用的方法来整理知识？
我： 我们主要沿用已有的业务知识体系，里面已经定义了一些术语及其含义，再结合具体业务的信息使用。生成 SQL 时，需要把相关知识提供给模型，帮助它理解用户到底在问什么。
问题 06
技术上做了哪些优化？问题改写是怎么做的？
我： 比较重要的一项是问题改写。
首先识别用户的查询意图，把涉及的字段、实体和过滤条件整理出来。其次，区分不同类型的过滤，比如针对原始记录的条件、和针对聚合结果的条件。最后，补充用户没有明确表达、但生成 SQL 又需要的业务语义。

追问： 改写也是让大模型来做吗？
我： 是的。需要把相关知识、表结构和必要的样例提供给模型，再通过提示词引导它完成改写。
后续生成时，会结合用户原始问题、改写结果、表结构和外部知识，生成多个候选 SQL，再进行评分和选择。这部分比较依赖模型能力，候选生成和选择本身没有特别复杂的手段。
刚才介绍的候选生成方案，是评测时采用的做法。
问题 07
能根据用户的问题找到对应的表吗，还是表已经选好了？
我： 这里需要再解释一下。这个 Text-to-SQL 组件主要是在已经选定表或数据集的前提下生成 SQL，找表由另外的检索工具负责。
在一些已确定的业务场景里，可选的表范围本来就比较固定，不需要每次从很大的表库里重新搜索。

你提到底层数据平台能加速查询，为什么会更快？
我： 核心是把原本放在查询较慢的数据源里的数据，整理到查询更快的引擎中。不同存储方式在容量、成本和查询速度上有不同取舍，通过额外的资源投入换取查询速度。具体的引擎和部署方式就不展开了。
问题 08
另一个通用任务智能体项目，也介绍一下吧。
我： 当时看到长任务 Agent 的效果，觉得这条技术路线值得尝试。我们之前更多采用工作流的方式，所以先有了做这个方向的想法，再去找适合的场景，最后选中了信息收集、报告生成、简单网页制作这些办公任务。
第一版很快就做出来了，核心是 Agent Loop：接收问题、调用工具、再把工具结果补充到上下文里，继续执行。后面花费更多时间的，是解决任务跑不长、运行不稳定，以及最终产物不符合要求这些问题。

我们也提前构建了评测集。一部分使用公开评测，一部分根据实际办公场景整理。因为公开评测中的一些题目，与我们实际要解决的问题并不一致。上线后，还会抽取实际任务，通过人工评价检查效果。
追问： 用户主要用它做什么？
我： 举一个我自己就在用的例子：把当天的工作沟通整理成日报，再保存到文档里。还有收集资料、生成报告、制作简单网页等场景。
问题 09
你觉得自己的主要优势是什么？
我： 自夸，略去，这里的重点是，要给详细的案例，不然一听就是吹的。
问题 10
你做过数据分析，也做过通用任务智能体，怎么看数据智能化接下来的发展？
我： 我觉得数据仍然是一个值得投入的方向。

从模型训练来看，不管是预训练、后训练还是微调，都需要数据。再看应用，我们前面聊到的那些场景，如果没有整理好的数据，AI 也很难发挥作用。
结构化和非结构化的数据，都需要经过整理，变成便于检索和使用的形式，才能支持后面的问答和长任务。我的判断是，数据和知识本身的价值，不会因为某一种 AI 技术的变化而消失。
问题 11
如果用今天的大模型，重新做当时的数据智能化工作，你会重点做哪些方向？
我： 如果现在让我重新做，我大概率不会先去开发一个通用智能体，而是先把已有能力整理成工具。
比如，把数据平台的接口通过 MCP、CLI 提供出来，把已经沉淀好的流程做成 Skill。取数、数据清洗、可视化，都可以做成相应的能力，再交给成熟的 Agent 使用。

办公场景可以采用本地 Agent 加 Skill、MCP 的方式。但如果要把这些能力变成线上服务，还需要解决部署、会话管理和稳定运行的问题。
所以我的设想是分成两部分：一部分服务本地办公，另一部分提供线上部署和托管能力，尽量复用两边的工具和流程。
问题 12
你现在负责 Agent 的部署和运维，觉得比较困难的地方是什么？
我： 主要还是状态管理。
Agent 在连续对话或执行任务时，需要记住前面的内容。比如这一轮对话还在进行，用户又补充了信息，或者任务停下来等待人工处理，都需要保留相应的状态。
我当时把它概括为“有状态的 Agent 和无状态的 Web 服务之间的协调”。解决思路是把 Agent 的状态和运行时分开，让状态不只保存在某一个执行实例里。

需要保留的内容，包括会话历史、记忆，以及等待人工处理时停在了哪里。下一次继续执行时，要能够重新关联这些记录。
这件事本身不算特别新的思路，难的是把需要保存的状态梳理完整。框架也需要支持相应的状态扩展，否则平台很难替它完成这部分工作。
问题 13
做 toB 是否符合你的规划？对之后的工作有什么预期？
我： 当然了，不然怎么面下去，具体回答略。
这次面试的复盘
最明显的问题还是项目介绍。开头我讲了很多背景，但面试官几次停下来问：你具体负责什么？我应该先把自己的负责范围说清楚，再讲产品怎么发展。否则对方很难分清，哪些是整个产品的能力，哪些是我做的。

准确率那一段没有答到点上。对方问的是“这个效果实际能不能用”，我先解释了数字怎么统计，后面又补了使用情况。统计口径当然要讲，但还应该说明：适合什么任务，哪些结果需要人工检查，出错以后怎么办。这些在当时的回答里没有交代清楚。

00 | Agent 做到什么程度，才算好？

04 | 模型越来越强，Agent 工程还剩什么？
这是这场面试里最难回答的一个问题。四个月之前，我确实没有系统地想过。回来仔细思考，发现还是有很多事情要做。
一个更好的模型，可能让原来的一些工程脚手架失去作用。那么，除了 LLM 本身的训练，哪些工程能力仍然值得深入？
下面四个方向，是我回来后的思考。
方向一 | 反馈闭环及其基建
模型再强，终究是概率模型，不能完全沿用过去写 CRUD 时处理确定性逻辑的方式。

使用评测集，持续测试、收集反馈、改进工程方案，是驱动 Agent 开发很重要的一种方式。
我想表达的是这套闭环的工作方式。它可能包含数据清洗、日志搜索、合并等技术，不能直接把它等同于 Loop Engineering。
方向二 | 分流、A/B 测试等运维能力
评测驱动的开发模式，离线评测是不够的。
上线以后效果怎么样？还需要 Agent 上线、流量分配、切流、对比测试等工作。
这些不是 Agent 时代才有的东西，但到了 Agent 场景，仍然需要反复去做。
方向三 | 知识工程（库）的构建
AI Agent 工程很核心的一件事，是组织、处理和传递给 LLM 的上下文，也就是上下文工程。
Prompt、Skill、RAG、Memory，都涉及上下文的存储、组织和传递。

但是，这些知识哪儿来？
那是知识工程的事情。Wiki、Graph 都是相关方案。
之前我写过《永不遗忘的 Agent：从 Memory 面试失败到构建生产级 Agent Memory》，这里不展开。
方向四 | 搜索与召回
知识库构建好了，如何快速、准确地找到对应的上下文，提供给 LLM 使用？
上下文终归有限。这是经典的搜索问题：BM25？Embedding？还是其他手段？在 LLM 的辅助下，还有哪些搜索方案？
在这几个方向深入，是我当时给自己的判断。即使模型继续变强，这些内容仍然值得投入。
这几个问题，我哪里没答好？
总体来说，我当时的感觉是：似乎一个都没回答好，所以觉得肯定凉了。

但这一面的价值，直到今天依然让我回味。除了压力面试的不适，更多的是对工程师发展和能力边界的思考。
