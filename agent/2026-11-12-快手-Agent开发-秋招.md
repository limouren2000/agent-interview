## 面经正文

今天分享一道快手的 Agent 面试题：Agent 会读用户文件、查数据库、调用外部 API，输入过滤、权限控制和输出脱敏该放在哪？

这题最容易只简单回答“进来时扫一遍，最后回复时脱敏”。但我认为真正容易漏的是中间这段：Agent 先从数据库读到用户信息，再调用 HTTP Tool，把内容发到外部地址。最后给用户的回答再干净，数据也已经出去了。

所以要沿着数据流设关口。进入模型前，用户文件、检索结果和 Tool Result 都要分类、按任务裁减；如果用第三方模型，发 Prompt 本身也要算一次出站。工具执行前，由 Runtime 按用户、租户、资源和操作做授权，数据库和文件系统还要有自己的权限边界。调用邮件、HTTP、Webhook 之前，再检查目标地址和请求参数；最终回答、Trace、Checkpoint 也不能漏。

这题让我想到自己写的框架：现在 Tool Executor 有独立的 ToolPolicy.authorize，Tool Descriptor 也记录了敏感级别。

但“允许读文件”和“允许发请求”分别通过，并不等于读出的内容可以发给那个接收方。真要补这一层，我会让 Tool Result 带来源和敏感标签，后续动作沿着标签检查数据去向；模型换种说法或做个摘要，也不能把标签洗掉。

面试里回答的时候，总体思路应该是这样：模型可以提出需要什么信息，访问权和外发权仍由 Runtime 与数据源决定。只盯最终回复做脱敏，拦不住工具链上的泄漏。

52. Agent 会读取用户文件、调用外部 API、访问数据库，你如何防止敏感信息泄漏？输入过滤、权限控制和输出脱敏分别应该放在哪里？
答：
这个问题本质上考察的是 Agent 的数据安全架构（Data Security）和信息流控制（Information Flow Control）。Agent 和传统后端最大的区别在于，模型能够自主决定读取什么数据、调用什么工具、把结果发送到哪里。如果没有严格控制，就可能通过 Prompt Injection、越权工具调用、跨租户检索或者外部 API，把用户的隐私信息、业务数据甚至系统密钥泄露出去。

我会采用 数据最小化 + 执行时权限控制 + 全链路 DLP（Data Loss Prevention）的设计。其中输入过滤主要放在数据进入模型上下文之前，权限控制必须放在 Tool Runtime 和真实数据源之间，输出脱敏则要覆盖最终回答和所有对外数据通道，而不仅仅是用户看到的文本。

1. 输入过滤应该放在哪里？
输入过滤首先应该放在 Input Gateway 和 Context Builder 两个位置。Input Gateway 负责检查用户输入、上传文件等原始数据，识别 Prompt Injection、恶意内容以及敏感信息；Context Builder 则负责检查 RAG 检索结果、数据库查询结果、Tool Observation 和长期记忆，因为这些数据虽然不是用户直接输入的，但同样会进入模型上下文。

具体实现时，可以先对数据进行分类，例如 PUBLIC、INTERNAL、CONFIDENTIAL、SECRET，然后根据当前任务决定哪些信息允许进入模型。对于身份证号、手机号、银行卡号、API Key 等敏感字段，可以使用规则匹配、NER 模型以及专用 PII Detector 识别，再进行删除、掩码或 Tokenization。开源的 Presidio 就提供了 PII 检测和匿名化组件，可以作为这一层的基础能力。

但不能简单地把所有敏感数据全部删除，因为某些业务任务确实需要使用真实数据。更合理的方法是 Data Minimization：只向模型提供完成当前任务必需的字段。例如用户查询账户余额，模型可能只需要知道余额和币种，不需要同时读取身份证、银行卡号和完整交易流水。如果只是需要引用一个敏感对象，可以使用占位符或资源引用，由可信 Runtime 在真正执行时解析，避免原始 Secret 进入模型上下文。

还有一个容易忽视的问题是：如果使用第三方模型 API，向模型发送 Prompt 本身就是一次数据出站。因此敏感数据是否允许发送给模型服务商，需要在 Model Gateway 做独立的出站策略检查，并根据数据等级选择允许的模型供应商、部署区域或者私有化模型。

2. 权限控制应该放在哪里？
• 权限控制必须放在 Tool Execution Boundary，而不能依赖 System Prompt。模型可以提出调用数据库、读取文件或访问外部 API，但不能因为模型生成了合法的 Tool Call，就认为这个操作已经被授权。
• 实际执行链路应该是：
LLM → Tool Call → Policy Engine → Authorization → Parameter Validation → Tool Executor
• 其中 Policy Engine 应该结合 User Identity、Agent Identity、Tenant、Resource、Operation、Risk Level 做决策。权限模型可以采用 RBAC 与 ABAC 结合的方式：RBAC 判断用户和 Agent 拥有哪些角色能力，ABAC 再结合资源所有者、数据等级、当前任务和操作参数实施细粒度控制。
• 例如 Agent 调用 query_account 时，不能仅仅判断它有没有调用该工具的权限，还要检查当前账户是否属于请求用户、能否查看对应字段、是否允许批量查询。数据库层最好进一步通过只读账号、行级权限（RLS）、列级权限或受控查询接口执行实际约束，防止 Agent 绕过应用层直接读取其他租户数据。

• 文件系统同样需要限制 Workspace 范围，通过 Sandbox、目录白名单和路径校验防止越权读取。外部 API 则应使用最小权限、短生命周期 Credential，并由 Credential Broker 在执行时注入，避免模型直接接触 API Key。
• 这其实是 Least Privilege（最小权限）与 Defense in Depth（纵深防御）：即使模型被恶意 Prompt 诱导，真实执行权限仍然掌握在确定性的 Runtime 和业务系统手里。
3. 输出脱敏应该放在哪里？
• 很多人会认为只需要在 Agent 最终回答用户时做一次脱敏，但这是不够的。因为 Agent 的数据泄漏不一定发生在最终 Response，也可能发生在工具调用过程中。
• 例如 Agent 先通过数据库工具读取用户隐私，随后调用 HTTP Tool，把数据提交到攻击者控制的接口。即使最后返回给用户的答案完全正常，敏感数据实际上已经泄漏。
• 因此输出控制至少要覆盖三个出口：Model Response、Outbound Tool Call 和持久化存储/日志。
• Model Response Gateway 在答案返回用户之前，根据用户权限做敏感信息检查和字段级脱敏。例如用户可以查看自己的手机号，但不能查看其他用户的手机号；同一份查询结果，管理员和普通用户看到的字段也可能不同。

• Outbound Tool Gateway 则在调用邮件、Webhook、HTTP、MCP 等对外工具之前，检查目标地址、请求参数和数据等级。尤其需要限制外部域名、网络出口和重定向，防止 Agent 把敏感数据藏在 URL、请求 Body 或其他工具参数中发送出去。相关 Agent 安全研究也指出，单纯检查最终文本无法覆盖这些隐藏的数据外泄通道。
• 日志与持久化同样属于数据出口。Trace、Checkpoint、Memory、Tool Ledger 都可能保存完整 Prompt 和 Tool Result，所以需要在写入前实施敏感字段过滤、访问控制及加密保护，而不能把数据库密码或个人隐私直接记录在可供多人查看的调试日志中。
4. 更进一步：跨工具的信息流控制
• 真正有技术深度的地方在于 Information Flow Control。
• 假设 Agent 同时拥有 read_private_file 和 send_email 两个工具。从单个工具权限来看，读取文件是合法的，发送邮件也是合法的，但两者组合起来就可能造成敏感信息泄漏。
• 因此不能只判断“这个工具能不能调用”，还要判断：
• 上一个工具读取的数据，是否允许流向下一个工具及其目标接收方？

• 可以给 Tool Result 和中间变量附加 Sensitivity Label、Source、Owner、Allowed Destinations 等元数据，并在后续工具调用时传播这些标签。例如从内部数据库读取的 CONFIDENTIAL 数据，默认不能通过外部 HTTP Tool 发送到未知域名。即使模型通过改写、摘要或编码改变数据形式，也不能因此自动降低数据敏感级别。
• 这种基于数据来源和传播路径的防护，比简单的关键词脱敏更可靠。CaMeL 等 Agent 安全研究也采用了类似的 Capability / Information Flow 思想。
5. 如何形成完整的安全闭环？
• 工程上可以将这些能力统一为 Security Gateway + Policy Engine + DLP Engine + Audit System。输入进入 Context 前做分类与最小化；每次 Tool Execution 前进行独立授权；模型响应和工具出站请求经过 DLP 检查；Memory、Checkpoint 和 Trace 按数据等级隔离存储。
• 还应该建立针对性安全评测，例如跨租户数据访问、恶意网页诱导外传、敏感数据进入第三方模型、URL 编码绕过脱敏、越权文件读取等测试。重点指标不仅是敏感内容识别率，更包括 Unauthorized Access Rate、Data Exfiltration Success Rate 和误拦截率，避免安全策略过严导致正常业务无法使用。

面试时可以这样回答
• 我会把 Agent 的敏感数据防护分成输入侧、执行侧和输出侧三层，并增加跨工具的信息流控制。
• 输入侧在 Input Gateway 和 Context Builder 中进行数据分类、Prompt Injection 检测、PII 识别和最小化处理，保证用户文件、RAG 文档和 Tool Result 不会把不必要的敏感信息直接带入模型。
• 执行侧在 Tool Runtime 中建立独立的 Policy Engine，通过用户身份、Agent 身份、租户、资源和操作类型进行细粒度授权，并结合数据库行列权限、文件 Sandbox、Credential Isolation 和最小权限控制，防止模型越权访问数据。
• 输出侧不只是对最终答案脱敏，还需要在所有对外工具调用前进行 DLP 检查，限制敏感数据流向未经授权的目标；同时保护日志、Memory 和 Checkpoint，防止间接泄漏。
• 最核心的设计原则是：模型可以决定需要什么信息，但不能自行决定自己有权访问什么信息，更不能自行决定敏感数据可以发送到哪里。权限由 Runtime 执行，数据流向由安全策略控制，脱敏只是最后一道防线，而不是主要安全机制。
