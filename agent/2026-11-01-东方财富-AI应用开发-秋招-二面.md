### 复盘版（发帖 2026-11-01）

今天来复盘一下东方财富的线下面试的内容

之前发笔记的时候就说到，感觉面试的时候闻到的问题挺有含金量的，面试官似乎更注重实际业务场景的问题，关于AI和后端都问的是一些场景的题目

因为之前参加过华为的线下面试，所以这一次对我来说也不算特别紧张和新鲜，还能有思路的回答一些问题。该说不说在南京玩的还是挺好的

1. 关于你提到的模型轮次、工具调用次数这些，你设置的默认值是根据什么来的？
• 设定依据：
- 任务复杂度：简单问答、单轮查询、复杂多步任务，默认预算一定不同。
- 工具必要性：如果问题大概率只靠模型就能答，工具上限就低；如果依赖检索、数据库、业务 API，上限就会提高。
- 风险等级：读操作、写操作、高危操作的预算不同，越高风险越强调保守和可控。
- 时延与成本：要同时考虑响应时间、Token 消耗、工具耗时和整体预算。
- 历史评测：根据成功率、P95 时延、坏例复盘、用户满意度持续调参。
• 常见控制项：
- 最大轮次 max_turns、最大工具调用数 max_tool_calls、单工具次数上限、总 Token 上限、超时上限。
- 还会设置 repair budget，防止无限修复和死循环。
• 实践方式：
- 一般先给保守默认值，再按场景分层：FAQ 场景偏小，复杂 Agent 场景偏大。
- 运行中如果发现收益递减、重复调用、低置信度不提升，就提前终止并触发澄清、降级或转人工。

2. 提到的 RAG 技术，除了这种来做检索以外你还了解什么？
• 我理解的 RAG 不只是“向量检索”：
- 稀疏检索：BM25、倒排索引，适合关键词精确命中。
- 稠密检索：Embedding + Vector Search，适合语义召回。
- 混合检索：Sparse + Dense + RRF 融合，通常比单一路径更稳。
- 重排：Cross-Encoder / Reranker，对候选结果做二次排序。
• 进一步增强：
- Query Rewrite：把用户问题改写成更适合检索的查询。
- Chunking：按语义切片、滑窗、父子块，提高召回质量。
- Context Compression：对召回内容压缩、去重、聚合，避免上下文过长。
- 结构化检索：SQL、图数据库、知识图谱检索，不只是文本库。
- Web Search / Tool Retrieval：让检索范围从知识库扩展到外部工具和实时信息。
- 引用与证据绑定：答案必须能回溯到来源，降低幻觉。
• 总结：
- 一个成熟的 RAG 体系通常是“多路召回 + 重排 + 压缩 + 引用 + 评测”，而不是只做。

3. 多跳推理你了解吗？说说怎么做的
• 我的理解：
- 多跳推理不是一次性猜答案，而是把复杂问题拆成多步，每一步都基于前一步证据继续推进。
• 常见做法：
- 第一步先做任务分解，把问题拆成若干子问题或查询目标。
- 第二步逐跳执行：每一跳检索、调用工具或查询数据库后，把结果写入中间状态。
- 第三步根据当前证据决定下一跳做什么，是继续检索、换关键词、换工具，还是已经足够回答。
- 第四步最后汇总所有中间证据，做一致性校验、冲突消解和答案生成。
• 实现关键点：
- 要有显式状态：当前进度、已收集证据、待解决问题。
- 要有停止条件：证据充足、预算用尽、置信度提升很小。
- 要有回退机制：某一跳失败或证据冲突时，可以重试、换路径或直接澄清。
- 最好配合引用来源，保证每一跳结果可追溯。

4. 关于 AI 安全相关的，如果遇到工具投毒和提示词注入，该怎么办？
• 核心原则：
- 把系统提示、用户输入、外部文档、工具输出严格分层，不能混成同等可信。
- 工具返回默认按“不可信数据”处理，而不是按“可信指令”处理。
• 抗提示词注入：
- 不盲从外部文本里的“忽略前文”“按我说的做”这类内容，只把它当普通数据。
- 在系统层明确规定：只有系统策略能改变行为，检索内容不能覆盖系统规则。
- 对高风险任务增加人工确认、二次校验和只读优先策略。
• 抗工具投毒：
- 对工具结果做 Schema 校验、字段白名单、内容清洗和敏感词检测。
- 工具最小权限原则：读写分离、敏感参数白名单、高危工具单独授权。
- 高风险执行放到沙箱或隔离环境，所有副作用操作记审计日志。
• 兜底策略：
- 一旦命中安全策略，就拒绝、降级、澄清或转人工，而不是继续自动执行。

5. 你是如何保证 AI 能够正确回答问题？
• 如果从 Harness 设计来讲，我会做几层保障：
- 入口层：先做意图识别、槽位提取、风险分级，判断是直接回答、走 RAG，还是走工具调用。
- 检索层：知识型问题先检索后回答，要求答案尽量绑定证据来源。
- 执行层：对工具调用做 Schema 校验、参数校验、权限校验和前置条件校验。
- 输出层：模型结果不能直接落地，要经过 policy、validator、repair 这几道关。
- 幂等层：通过 Tool Ledger 或请求 ID，避免副作用操作重复执行。
- 恢复层：做 checkpoint / resume，服务重启后能继续执行而不是重复乱跑。
• 持续优化：
- 用日志、评测集、回放、badcase 复盘不断修正提示、规则和策略。
- 核心目标不是“让模型自由发挥”，而是让系统始终在可控边界内回答。

6. 在你这个场景下，用户提出了一个很复杂的问题，模型是如何能够知道用户的需求？
• 核心思路：理解需求不是一次分类，而是一个结构化过程。
- 先识别主意图：用户到底是在问知识、查数据、做操作，还是售后诉求。
- 再抽取关键约束：对象、时间、数量、目标、限制条件、优先级。
- 结合上下文、历史会话、短期记忆和当前系统状态补全缺失信息。
- 如果一个问题其实包含多个子任务，就先拆解，再分别规划执行路径。
- 低置信度或高风险场景不猜，必须主动澄清。
• 产出结果：
- 最终不是只输出一句“我理解了”，而是形成结构化 goal：主意图、子任务、约束、所需工具和预期输出。
- 本质上就是“理解—补全—拆解—确认—执行”五步。

7. 那你的项目中意图识别是如何做的？
• 当前方案：
- 先做粗粒度路由，判断是知识问答、任务执行、售后场景还是澄清类请求。
- 再做细粒度识别，把请求映射到更具体的意图类型。
- 在识别意图的同时，抽取槽位、实体和约束条件，形成结构化目标。
- 结合规则校验和置信度分数，避免把一个请求错误拆成多个目标。
- 对低置信度结果进入澄清路径，对高风险结果进入更严格的安全检查。
- 将意图识别结果和后续执行结果做闭环，用 badcase 反向修正规则、提示和标签体系。
• 我更看重的点：
- 不是只看分类对不对，而是看识别结果能不能真正支撑后续规划和执行。

8. 除了你提到的这种做法以外，还有什么你了解的做意图识别的方案？
• 常见方案：
- 关键词 / 规则：实现快、可控强，但泛化差，规则维护成本高。
- 传统文本分类：比如 BERT 分类器，适合固定意图集合、标签边界清晰的场景。
- 向量相似度检索：把用户问题和意图库做 embedding 匹配，适合标准问法较多的场景。
- 联合意图 + 槽位抽取：边识别意图边抽实体，适合任务型对话。
- LLM 分类：零样本/少样本能力强，适合开放场景和复杂表达。
- 分层识别：先粗后细，适合意图数量多、层级复杂的业务。
- 混合方案：规则 + 分类器 + LLM 裁决，通常在真实业务里最稳。
• 演进方向：
- 还可以加入主动学习、错误样本回流、在线校准，让意图系统持续进化。

9. 一个 AI 场景题（以智能客服为例）
• 如果让我设计，我会按四层来做：
- 接入层：负责会话管理、用户身份、渠道接入、上下文组装。
- 编排层：负责意图识别、任务拆解、RAG、澄清、规划和工具选择。
- 执行层：负责查询知识库、调用业务 API、写工单、转人工或触发业务流程。
- 治理层：负责权限、风控、审计、预算控制、评测和故障恢复。
• 关键原则：
- 对只读问题强调准确性：检索优先、证据优先、引用优先。
- 对高危操作强调安全性：二次确认、最小权限、人工兜底。
- 对复杂问题强调可恢复：中间状态持久化，失败可重试、可回退。
- 对全链路强调可观测：日志、链路追踪、坏例回放和评测闭环。
• 如果被继续追问：
- 我会补充人工转接策略、预算分级策略以及会话摘要和记忆管理。

10. 遇到过 Full GC 的情况吗？你会如何排查问题？
• 排查顺序：
- 先看现象：Full GC 频率、单次停顿时长、是否已经影响 RT、QPS 和超时。
- 再看监控：堆使用率、Old 区增长、对象晋升速度、GC 前后回收效果。
- 再看 GC 日志：是什么收集器、何时触发、回收是否有效。
- 再做 dump：分析大对象、可疑引用链、对象分布，判断是否内存泄漏。
• 常见原因：
- 缓存打满、大对象进入老年代、线程池积压、频繁创建临时对象、静态集合泄漏。
• 优化思路：
- 优先改代码和对象生命周期，其次调整缓存策略，再根据情况调堆大小和收集器参数。

11. Redis 缓存在你们项目里是怎么用的？
• 常见用途：
- 热点数据缓存：减轻数据库压力，提高读性能。
- 会话与状态缓存：比如登录态、验证码、限流计数器。
- 分布式锁与幂等：控制并发和避免重复提交。
- 消息 / 排队辅助：例如延时队列、短期任务协调。
- AI 场景还可以缓存检索结果、Prompt 模板、会话摘要、短期记忆和中间结果。
• 设计要点：
- 需要设置合理 TTL，避免无界增长。
- 需要考虑缓存一致性、缓存击穿 / 穿透 / 雪崩防护。
- 热 Key、大 Key 和淘汰策略都要重点关注。
- 不是所有数据都缓存，适合高频读、可接受短暂不一致的数据。

12. 你们部署 Redis 使用的是什么模式？你知道都有哪些？
• 常见部署模式：
- 单机模式：简单，适合开发环境或低并发场景。
- 主从复制：主写从读，提升读能力，也方便做高可用基础。
- Sentinel：在主从基础上增加自动故障转移。
- Cluster：分片集群，解决更大容量和更高并发问题。
• 如何选择：
- 数据量不大、要求不高时可单机。
- 需要高可用时至少主从 + Sentinel。
- 数据量和并发都上来后，通常选择 Cluster。
- 线上最终怎么选，要看容量、可用性、成本、运维能力和业务 SLA。

13. Redis 线上如果内存突然满了，会是什么情况导致的？如何排查？
• 常见原因：
- 大 Key 过多，或者某类对象无上限增长。
- TTL 设置不合理，大量键不过期或过期过慢。
- 缓存雪崩后大量回填，短时间把内存打满。
- 热点业务暴涨，写入量远超预期。
- AOF 重写、复制缓冲区、客户端输出缓冲额外占用内存。
- 内存碎片率过高，看起来“还有内存”，但实际可用不足。
• 排查方法：
- 先看 used_memory、maxmemory、evicted_keys、hit rate、slowlog。
- 再排查 bigkey、hotkey、Key 数量分布、TTL 分布和对象编码。
- 结合最近业务变更、流量波动、持久化任务和主从同步情况一起判断。
• 处理思路：
- 删除无效 Key，限制大 Key，优化 TTL，设置淘汰策略，必要时扩容。

14. 假设现在有一张表，有十亿数据量，要加一个字段，你会怎么做？
• 核心原则：不停机、可回滚、分阶段、先兼容后收口。
• 处理步骤：
- 先判断是否必须立即物理加列，能否通过逻辑兼容先支持。
- 如果必须执行，优先选择在线 DDL，避免长时间锁表。
- 先做代码兼容：让应用同时兼容新旧 schema。
- 在低峰期变更，观察主从延迟、锁等待、业务 RT 和错误率。
- 如果新字段需要历史数据回填，采用分批、异步、限速回填，避免一次性全表更新。
- 灰度发布完成并验证稳定后，再逐步收口旧逻辑。
• 面试里可以补充：
- 如果是 MySQL，还要关注版本、online DDL 能力、索引影响和回滚方案。
