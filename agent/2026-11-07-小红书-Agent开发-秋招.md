## 面经正文

分享一道看过的小红书的面试题：用户先用模型 A，任务做到一半切到模型 B。A 留下的摘要如果写错了，B 怎么知道？用户最早说的限制又怎么保证还在？

举个例子，用户原话是“先分析问题，不要改代码”。A 的摘要只留下“需要修复这个 bug”。B 如果只看摘要，就可能直接动文件。这里出错的不是 B 忘性大，而是交接时把模型的概括当成了用户指令。

最近写框架的时候，我就在处理类似的来源边界：TaskInput 保留用户原话，TaskFrame 存模型对任务的解释，并标明 model_inference。第 50 题把这条边界延伸到了跨模型交接，但不等于项目已经实现了完整的模型切换。

我的回答会分三份存：1.用户目标、禁止项和验收条件，保留原文及版本；2.实际做完了什么，关联工具回执；3.模型 A 写的摘要，只用来帮助 B 快速理解，并给关键判断附上原始消息或结果的引用。

切到 B 时，由 Runtime 重新组装上下文：先放当前有效的用户约束和任务状态，再放核对过的摘要。窗口不够，先压缩历史描述，不能把“不要改代码”压没了。如果若说“已完成”，还得回查是否真有执行记录；后续用户修改要求，也要更新约束版本。

最后一道关口在执行前。B 即使理解错了，工具调用仍要对照当前约束检查。摘要负责省阅读成本，不能替用户发号施令。

50. 用户先使用模型 A，随后切换模型 B，怎样避免旧模型生成的摘要污染新模型的上下文？如何保证原始关键约束不丢失？
答：
这个问题本质上考察的是 Cross-Model Context Handoff（跨模型上下文交接）和 Context Integrity（上下文完整性）。
模型 A 生成的摘要可能包含事实遗漏、错误推断、过度概括，甚至带有模型 A 特有的表达和推理偏好。如果切换到模型 B 后直接把这份摘要当成可信上下文，就可能产生 Summary Contamination（摘要污染）和 Error Propagation（错误传播）。因此核心原则是：摘要只能是上下文的压缩表示，不能成为任务事实和用户约束的唯一真相来源。
1. 第一步是分离原始约束与生成式摘要。
在 Context Engineering 中，我会将上下文分为三个部分：一是用户明确提出的目标、硬性约束和验收条件，形成独立的 Goal Contract / Constraint Store；二是当前任务进度、已完成步骤、关键决策等结构化 Task State；三是模型根据历史对话生成的 Conversation Summary。前两者属于持久化的权威状态，第三者只是辅助理解历史的信息。无论模型如何切换、摘要如何压缩，原始约束都不应该依赖 LLM 自己记住，而应该由 Runtime 从持久化存储中重新注入。

2. 第二步是对摘要做结构化和来源追踪。
• 不建议让模型 A 生成一大段自由文本后直接传给模型 B，而是要求摘要按照统一的 Handoff Schema 输出，例如 goal、completed_tasks、pending_tasks、decisions、observations、uncertainties、source_refs。每个重要事实最好关联原始 Message ID、Tool Observation 或 Artifact 引用，并标注来源和可信程度。这样模型 B 接收到的不是模型 A 的自由发挥，而是一份能够追溯到原始证据的任务交接记录。尤其要避免把摘要中模型自行推断的内容提升成 System Instruction。
3. 第三步是增加 Summary Verification。
• 模型切换前，可以通过确定性校验器和独立的语义 Verifier 检查摘要是否与原始任务状态一致。重点检查用户硬性约束是否被遗漏、已完成任务是否真实完成、技术决策是否被错误改写，以及是否产生了没有证据支持的新事实。对于结构化字段可以直接做 Schema 和状态一致性检查，对于语义层面的事实则回查原始消息或工具结果。验证失败时，应该重新从原始证据生成摘要，或者标记不确定信息，而不是让模型 B 继续继承错误内容。

4. 第四步是由 Runtime 重新构建模型 B 的上下文，而不是直接复用模型 A 的 Prompt。
不同模型的 Tokenizer、Context Window、Tool Calling 格式、指令遵循能力可能不同，因此切换时应该通过统一的 Context Builder，把权威任务状态、经过验证的摘要、近期消息和必要证据转换成适合模型 B 的上下文。这里可以采用分层 Token Budget：原始关键约束必须优先保留，当前任务状态其次，历史摘要和低价值 Tool Result 最后。如果模型 B 的窗口较小，应优先压缩历史，而不是压缩掉核心约束。
还要注意，不同模型或 Provider 的原生 Compaction 表示不一定能够直接互通。如果模型 A 使用了 Provider 特定的压缩格式或内部状态，切换到 B 时应该回到模型无关的原始消息、结构化 Task State 和可追溯摘要，重新生成 B 的上下文，而不是假设某种压缩状态能够跨模型无损迁移。
5. 第五步是处理约束冲突与版本更新。
原始约束虽然需要保留，但并不意味着永远不能修改。如果用户在后续对话中明确改变目标或约束，应通过 Runtime 更新 Goal Contract 的版本，并保存修改来源、时间和旧版本。冲突处理应优先考虑有效的用户明确指令和当前任务授权，而不是简单地让“最近的一条摘要”覆盖旧约束。模型 A、模型 B 都没有权限自行修改用户的硬性约束。

6. 第六步是建立切换后的行为校验机制。
模型 B 开始执行以后，Runtime 仍然需要在关键 Action 前检查 Goal Alignment 和 Constraint Compliance。例如模型 B 计划执行某个工具调用，系统应判断这个动作是否符合原始目标、是否违反禁止操作、是否超出授权范围。对于高风险动作，校验失败必须直接阻断；对于一般性的任务理解偏差，可以触发 Context Repair，重新注入关键约束或召回原始证据。这能够防止摘要虽然通过初步验证，但模型 B 在后续执行中仍然错误理解约束。
最后还需要建立专门的 Cross-Model Handoff Evaluation。测试时让模型 A 执行一段长任务，生成摘要并切换到模型 B，然后检查关键约束保留率、任务状态继承准确率、错误事实引入率以及最终任务成功率。对于关键约束，重点不仅是它有没有出现在 Prompt 中，还要验证模型 B 实际执行时是否遵守。对于无法从摘要恢复的信息，系统应该能够回查原始记录，而不是强行猜测。

面试时可以这样回答
我不会直接把模型 A 生成的 Summary 当成模型 B 的可信上下文，而是采用 Model-Agnostic Context State + Structured Handoff + Verification + Context Reconstruction 的设计。
首先将用户原始目标、硬性约束和验收标准单独持久化，形成版本化的 Goal Contract；将任务进度、工具执行结果和关键决策维护在 Task State 中。模型 A 生成的摘要只作为辅助上下文，并要求包含原始证据引用，通过 Schema Validation 和事实一致性校验后才能用于交接。
切换模型时，Runtime 根据模型 B 的上下文窗口和协议重新组装 Prompt，优先注入原始关键约束和当前任务状态，再按需加入经过验证的摘要和历史证据。模型 B 执行期间继续通过 Goal Alignment Monitor 和 Constraint Verifier 检查行为是否偏离目标。
最核心的思想是：模型可以生成、压缩和理解上下文，但不能成为关键任务状态与用户约束的唯一维护者。原始事实由持久化存储保证，约束完整性由 Runtime 保证，摘要只承担信息压缩和辅助推理的职责。
