1. Agent 与固定 Workflow 的边界是什么？（追问：你会根据哪些条件决定是否引入自主决策能力？）
• 固定 Workflow 适用场景：
- 任务流程稳定、步骤明确、可完全规则化，结果可预测且确定性强。
- 对合规性、可控性、稳定性要求高的场景（如风控、财务、审批等）。
• Agent 适用场景：
- 任务开放、存在较大不确定性，需要自主规划、选择工具、动态调整步骤。
- 需要处理复杂目标、环境变化、长链路任务，或依赖外部实时信息的场景。
• 决定是否引入自主决策能力的关键条件：
- 任务不确定性：输入是否多样、目标是否模糊、是否存在多种可行路径。
- 路径可枚举性：是否可以用固定规则/流程覆盖大部分情况。
- 外部信息需求：是否需要实时查询外部知识、工具或环境交互。
- 成本与风险：自主决策可能带来的错误成本、合规风险是否可接受。
- 可观测性与控制：是否需要对执行过程进行监控、干预或回滚。
• 最佳实践：
- 采用“固定 Workflow + Agent 节点”的混合模式。
- 将稳定、确定的步骤用 Workflow 固化，把需要推理、规划或外部交互的部分交给 Agent。

2. 介绍一些 langchain 和 langgraph，分别说说他们的核心概念
• LangChain（更高层的应用框架）：
- 核心概念：提供构建 Agent 应用的组件和封装，关注“有什么组件可以用”。
- 主要组件：Model（模型调用）、Prompt（提示模板）、Tools（工具集成）、Agent（代理策略）、Middleware（中间件）、Retriever（检索增强）、Structured Output（结构化输出）等。
- 作用：简化 LLM 应用开发，快速组合各类能力，适合构建常见的 Agent 应用。
• LangGraph（更底层的运行时与编排框架）：
- 核心概念：基于图的状态机，用于构建可控、可持久化、可中断的 Agent 执行流程。
- 主要概念：State（全局状态）、Node（节点）、Edge（边）、Conditional Edge（条件边）、Reducer（状态合并）、Checkpointer（检查点持久化）、Interrupt（中断机制）、Store（状态存储）等。
- 作用：提供更灵活的底层编排能力，支持复杂的多轮、长时运行的 Agent 工作流。
• 二者关系：
- LangChain 关注“Agent 有哪些能力组件”，提供上层抽象和易用的接口。
- LangGraph 关注“Agent 如何执行和编排”，提供底层的状态管理和运行时能力。
- 通常结合使用：用 LangChain 构建组件，用 LangGraph 编排复杂的执行流程。

3. 用户问题存在歧义时，Agent 如何判断应该查询改写，补全上下文还是向用户澄清？
• 先判断歧义类型：
- 缺少关键信息（槽位缺失）：如时间、地点、对象、数量等未明确。
- 存在多种可能意图：同一个问题可能对应不同的业务场景或操作。
- 上下文不足：无法确定用户当前任务、历史背景或相关约束条件。
• 查询改写（Query Rewrite）：
- 当用户意图基本明确，但表述不规范、不完整或包含歧义词时，对问题进行改写以提高检索效果。
• 补全上下文：当可以从对话历史、长期记忆、用户画像或任务状态中获取缺失信息，且补全的置信度较高、风险较低时。
• 向用户澄清：当存在多种合理解释且会导致不同的执行结果，或涉及高风险操作（如修改、删除、支付等）时。
• 决策依据：综合考虑意图置信度、歧义带来的风险、补全信息的可获得性以及澄清的预期信息增益。

4. RAG 中怎样提升召回率？
• 核心方向：
- 从数据、检索和查询处理三层一起优化，目标是先提高 Recall，再用重排保证 Precision。
• 数据侧：
- 优化 Chunk 切分与重叠，保留标题、段落、表格、代码块等结构。
- 建立多粒度索引，避免关键信息被切碎。
• 检索侧：
- 采用 Hybrid Retrieval，把 BM25 等稀疏检索和向量检索结合起来。
- 可用 RRF 融合多路召回，再用 Cross Encoder 或 LLM Rerank 精排。
• 查询侧：
- 做 Query Rewrite、同义词扩展、Multi-Query、HyDE，
- 把用户问题改写成更适合检索的表达。
• 过滤与扩展：
- 合理使用 Metadata Filter，避免过滤过严造成漏召回。
- 复杂问题可做多跳检索或引入 GraphRAG。
• 评测指标：
- 重点看 Recall@K、Hit Rate、Coverage 和 Bad Case，而不仅仅看最终生成答案。

5. Agent 拥有发消息、修改数据或执行代码等副作用工具时，如何保证重复执行不会造成重复操作？
• 核心原则：
- 不要只依赖模型“记住别重复”，而是把副作用动作设计成幂等。
- 目标不是理论上的 exactly-once，而是工程上的 effectively-once。
• 幂等键设计：
- 为每个逻辑业务动作生成稳定的 Idempotency Key。
- 同一业务动作重复重试时，应复用同一个 key，而不是重新随机生成。
• Tool Ledger：
- 记录 logical_action_id、tool_call_id、参数哈希、状态、结果、外部业务单号和时间。
- 执行前先查 Ledger，若已成功则直接复用结果，不再重复发起。
• 外部系统配合：
- 支付、发消息、创建订单等接口最好原生支持幂等。
- 如果外部系统不支持，则用唯一约束、状态机、业务主键在业务层兜底。
• UNKNOWN 状态处理：
- 请求发出后如果进程崩溃，不能盲目重试。
- 应先调用查询接口或通过业务单号做 reconcile，再决定继续、补偿或人工介入。
• 高风险动作：真正不可幂等的副作用应结合 Compensation 或 Human Approval。

6. Agent 执行到一半服务重启时，如何从 Checkpoint 恢复，并避免已经完成的步骤被重复执行？
• Checkpoint 保存什么：
- 不仅保存 messages，还要保存 Run / Turn / Attempt、当前节点、计划、预算、工具执行状态、Workspace 引用等运行时状态。
• 恢复流程：
- 服务重启后先加载最近有效的 Checkpoint，再结合 Event Log 恢复到正确执行位置，而不是从头开始。
• 避免重复步骤：
- 恢复时先检查 Tool Ledger。
- SUCCEEDED：直接跳过并复用结果。
- FAILED：按策略重试。
- UNKNOWN：先核对外部真实状态，再决定后续动作。
• 幂等配合：
- 副作用步骤必须配合幂等键和业务唯一约束，否则即使恢复了状态，也可能把外部动作重复执行。
• 并发安全：
- 通过 Lease 或 Fencing Token 防止旧 Worker 复活后继续提交结果，避免两个 Worker 同时推进同一任务。
• 核心关系：
- Checkpoint 解决“状态恢复”，幂等键和 Tool Ledger 解决“副作用步骤不能随便重放”。

7. 短期记忆和长期记忆分别应该保存什么？（追问：如果记忆写入错误，如何发现、修正和淘汰？）
• 短期记忆：
- 保存当前会话和当前任务直接相关的信息，如最近对话、当前目标、计划、Tool Observation、中间变量和临时约束，本质上是 Working Memory。
• 长期记忆：
- 保存跨会话复用的信息，如稳定用户偏好、长期事实、项目背景、重要历史结论和可复用经验，但不等于把所有聊天永久保存。
• 写入策略：
- 每轮对话可以做 Memory Candidate 提取，但不应每轮强制新增；应经过 Write Gate，做价值判断、去重、Merge、冲突检测和置信度评估。
• 发现错误：依靠 Provenance、时间戳、用户反馈和后续事实冲突来识别错误记忆；用户显式更正通常优先级最高。

8. 多 Agent 系统中，主 Agent 如何拆分任务并判断某个子任务应该交给哪个子 Agent？
• 先做任务分解：围绕最终目标把复杂任务拆成若干可验证的子目标，明确每个子任务的输入、输出、约束、依赖和完成条件，形成 Task DAG。
• 拆分原则：只有在子任务相对独立、耦合较弱、可以并行或需要不同专业能力时才值得拆；强依赖任务硬拆会增加协调成本。
• 路由依据：看子 Agent 的专业领域、可用 Tool、数据权限、模型能力、成本、延迟、历史成功率和当前负载。
• 常见做法：为每个 Agent 建立 Capability Registry，主 Agent 或 Router 根据任务特征做打分匹配，选择最合适的执行者。
• 预算控制：主 Agent 还要控制并发度、Token 预算、时间预算和失败重试策略，避免为了多 Agent 而多 Agent。
• 本质角色：主 Agent 更像 Orchestrator，负责分解、路由、汇总和验收，而不是把所有事自己重做一遍。

9. 多个子 Agent 给出相互冲突的结果时，主 Agent 如何判断应该采信、重新执行还是请求人工介入？
• 不能简单多数投票：先比较证据质量、来源可信度、数据新鲜度、推理链完整性和结果是否满足约束。
• 可验证任务优先让外部事实裁决：例如数据库查询、编译测试、搜索结果、规则引擎，而不是再让一个 LLM 凭感觉判断。
• 如果冲突来自推理过程：可用独立 Verifier 或 Judge，对“证据支持度、完整性、约束满足度”做评分，再决定采信哪一个。
• 如果怀疑某个子 Agent 偶然失误：可以换模型、换工具或换采样重跑关键步骤，而不是整条链路全部重做。
• 当冲突持续存在且会影响高风险操作时：应升级 Human-in-the-loop，由人工做最终裁决。
• 工程上要记录冲突内容、裁决依据和最终 Decision，便于审计、复盘和后续评测。

10. Function Calling、MCP 和 Skill 分别解决什么问题？为什么它们不能简单地相互替代？
• Function Calling：解决“模型如何按 Schema 发起一次工具调用”，重点是工具选择、参数生成和结构化调用，它更像 Model 到 Runtime 的调用接口。
• MCP：解决“外部 Tool、Resource、Prompt 如何以统一协议被发现、连接和调用”，重点是 Client 与 MCP Server 的标准化能力发现、连接和授权。
• Skill：解决“如何把某个可复用任务能力封装起来”，它通常不仅包含 Tool，还包含 Prompt、规则、步骤、示例和领域知识，属于更高层能力包。
• 三者抽象层次不同：Function Calling 是调用机制，MCP 是协议与连接标准，Skill 是能力组织与复用方式。
• 关系上，一个 Skill 可以内部使用多个 MCP Tool，而 MCP Tool 最终也可能通过 Function Calling 被模型选中调用。
• 因此它们不是互相替代，而是位于不同层次，常常需要组合使用。

11. Agent 生成的结构化 JSON 不符合 Schema 时怎么办？
• 预防优先：尽量使用 Provider Structured Output、JSON Schema 或 Constrained Decoding，从生成阶段限制输出空间。
• 校验分两层：先做 Syntax / Schema Validation，再做业务语义校验，例如字段范围、必填关系、枚举值和跨字段约束。
• 失败恢复：把机器可读的 Validation Error 返回模型，让它只修复出错字段并进行有限次数 Retry，而不是整条链路无限重跑。
• 保守修复：对缺逗号、缺引号等纯语法问题可以做 Parser Repair，但不要静默篡改业务语义。
• 多次失败后要 Fail Closed：走降级逻辑、返回安全默认值或请求人工处理，避免把格式错误扩散到后续系统。
• 同时沉淀 Bad Case，用 Format Compliance、Retry Rate 等指标持续优化 Prompt 和模型。

12. 如何为不同任务动态选择模型？
• 先抽取任务特征：任务类型、推理复杂度、上下文长度、是否需要 Tool Calling、是否多模态、风险等级、延迟 SLA 和成本预算。
• 维护 Model Profile：记录不同模型在推理、代码、长上下文、工具调用、稳定性、成本和延迟上的能力画像。
• 常见策略是 Small-first：简单分类、抽取、改写先走小模型；复杂推理、长链任务或低置信结果再升级到更强模型。
• 路由方式可以是规则路由，也可以是 Router Model / Classifier，但都要有可解释的切换依据。
• 线上还要有 Fallback 和 Circuit Breaker：模型超时、不可用或连续失败时自动切换备选模型。
• 高风险任务不能只为了省钱降级模型，应综合质量、成本和风险做决策。

13. Prompt、模型和工具版本同时变化时，如何设计版本记录，保证线上结果可复现？
• 核心做法是为每次执行保存不可变的 Run Manifest，至少记录 Agent/Harness 版本、Prompt Template 版本及渲染后 Hash、Model Provider/Model ID/参数、Tool 版本和 Schema Hash。
• 还要记录 Skill / MCP 版本、Retrieval Index Snapshot、Memory Snapshot 或引用、代码 Commit、Container Image、Feature Flag、Policy 版本和环境配置。
• 执行过程保留 Trace：模型输入输出、Tool Call、Tool Observation、Checkpoint、Event、Token 和关键随机参数，保证事后可追溯。
• 严格的完全复现并不总能做到，因为远程模型和外部 API 可能非确定；工程目标通常是“可追溯 + 可回放”。
• 必要时可把外部 Tool Result 固化下来做 Replay，这样定位 Bad Case 时能知道到底是 Prompt、模型、工具还是数据导致问题。
